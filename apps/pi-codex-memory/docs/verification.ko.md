# 검증 결과

[English](verification.md) | **한국어** | [README](../README.ko.md)

pi-codex-memory를 어떻게 검증하는지와 그 결과입니다. 코드를 바꿀 때마다 모델 없이 도는 검사를 실행하고, 기억이 실제로 효과가 있는지는 실제 모델로 정해 둔 시나리오를 돌려 확인했습니다.

## 결과 요약

- 기억을 켜면 새 세션에서 과거 결정 6개를 모두 답했고, 끄면 하나도 답하지 못했습니다. 두 모델 모두 같았습니다.
- 대화를 압축한 뒤에도 원래 사용자 발언 16개가 모두 추출 입력에 남았습니다.
- 대화에서 정정한 값은 새 세션 답변에 반영됐고, 메뉴에서 잊은 사실은 다시 생성되지 않았습니다.
- 기억 생성(추출과 통합) 한 번에 Haiku는 38,632토큰, Luna는 21,822토큰을 썼습니다.
- 실제 Pi 프로세스로 확인했을 때 닫은 대화만 한 번씩 기억이 되었습니다. 작업을 맡은 프로세스를 강제로 종료하자 90초 뒤 다른 세션이 이어받았습니다.

## 코드를 바꿀 때마다 하는 검사

저장소 루트에서 실행합니다. 어느 명령도 모델을 호출하지 않습니다.

```sh
pnpm --filter "@buyong/pi-codex-memory..." build
pnpm --filter @buyong/pi-codex-memory typecheck
pnpm --filter @buyong/pi-codex-memory lint
pnpm --filter @buyong/pi-codex-memory test
python3 apps/pi-codex-memory/verification/tui-smoke.py
node scripts/codex/check-package.mjs apps/pi-codex-memory
```

| 명령 | 확인하는 것 |
| --- | --- |
| `typecheck`, `lint` | 타입 오류와 Biome 규칙 |
| `test` | 테스트 145개. 격리한 저장소와 가짜 모델 응답으로 추출·통합·조회, 인용 검증, 정정·잊기, 취소, 저장소 공유와 읽기 동의를 확인합니다. 저장소 하나를 함께 쓰는 여러 세션을 가짜 시계로 돌려 백그라운드 작업 분담도 확인합니다. 범위마다 작업을 맡는 세션이 하나인지, 닫은 대화만 처리하는지, 동시에 최대 8개인지, 임대가 끊기거나 컴퓨터가 오래 잠든 뒤 다른 세션이 이어받는지, 공급자가 취소를 무시해도 종료가 끝나는지, 모든 세션에 작업 상태가 표시되는지, **Create memories now**의 두 기간 선택이 동작하는지를 봅니다. 기간 경계, 세션 제외 조건, 변경 없는 대화와 잊은 기억의 재생성 방지, TUI/RPC의 선택 취소도 확인합니다. 긴 세션도 확인합니다. 이미지가 든 16 MiB 넘는 세션 파일, compaction 지점에서 나눈 구간과 대화가 늘어도 바뀌지 않는 구간 ID, fork가 함께 쓰는 구간, 닫힌 구간이 원래 구간의 기억을 대신하는지, 대화 도중 붙인 저장소 정보, 처리할 것이 없는 파일을 나중 프로세스가 다시 읽지 않는지를 봅니다. 요청 한 번에 다 들어가지 않는 기억이 최근 대화부터 여러 번에 나눠 모두 요약에 반영되는지도 봅니다. DB 하나에 연결 두 개를 열어, 한 세션이 하다 만 요약을 다른 세션이 이어 가는지와 두 세션이 동시에 돌아도 같은 요청을 다시 보내지 않는지 확인하고, DB를 열면 버전이 2로 오르는지도 봅니다. `create-memory` 스크립트는 Pi 설정에서 불러온 가짜 모델 공급자로 실행해 봅니다. 일부 테스트는 실제 Pi SDK에 확장을 올려 명령과 도구를 실행합니다. |
| `tui-smoke.py` | 실제 Pi TUI에서 `/codex-memory`를 열어 항목, 커서가 있는 줄의 설명, 키 안내를 확인하고 **Memory model** 목록을 엽니다. 이어서 `/codex-memory-settings`를 열고, `/reload` 뒤 `/codex-memory`를 다시 엽니다. 생성 범위 선택을 열고 취소한 뒤, 대상 대화가 없는 상태에서 **All closed conversations**를 실행합니다. 모델 요청이 하나라도 나가면 실패합니다. `pi`가 `PATH`에 있어야 합니다. |
| `check-package.mjs` | 배포 아카이브에 필요한 파일과 진입점이 들어 있는지 확인합니다. |

설치한 패키지로도 한 번 확인했습니다. 이 패키지만 설치한 경우와 `@buyong/pi-codex` 번들로 설치한 경우 모두 확장이 로드됐고, 저장소 공유 사례 41개와 도구 사례 6개가 통과했습니다.

## 실제 모델로 한 검증

아래 작업 분담 검사는 생성 범위 선택 기능을 넣기 전 버전으로 했습니다. 범위 선택은 위의 모델 없는 테스트와 TUI 검사로 확인했으며, 실제 모델 검사는 다시 실행하지 않았습니다. 그 뒤의 회상 검사는 저장소 공유, 지금의 명령 구성, 백그라운드 작업 분담을 넣기 전 버전으로 했고, 이 세 가지는 작업 분담 검사와 위의 자동 검사로 확인했습니다.

### 백그라운드 작업 분담

`verification/live/coordinator.py`는 임시 폴더 하나에서 실제 Pi TUI 프로세스 여러 개를 `claude-bridge/claude-haiku-5-5`로 실행합니다. `pi`가 `PATH`에 있고 Claude Code에 로그인되어 있어야 하며, 요청을 열다섯 번 남짓 보냅니다. 실행 시간을 줄이려고 **Create memories after**와 **Update the summary every**를 1분으로 둡니다.

```sh
python3 apps/pi-codex-memory/verification/live/coordinator.py
```

1. 기억이 꺼진 상태에서 열린 세션은 아무것도 기록하지 않아야 합니다. 바깥에서 기억을 켜면 그 세션이 30초 안에 열려 있다고 기록하고 작업을 맡습니다.
2. 두 번째 세션은 결정을 남기고 종료합니다. 세 번째 세션은 다른 결정을 남기고 열어 둡니다. 네 번째 세션은 대화 없이 열어 둡니다.
3. 닫은 대화는 기억이 되어야 하고, 열어 둔 대화는 대기 시간보다 오래 멈춰 있어도 기억이 되지 않아야 합니다.
4. 작업을 맡은 프로세스를 강제로 종료합니다. 다른 세션이 이어받고, 남은 대화를 닫으면 기억이 되어야 합니다.
5. 다섯 번째 세션은 세 번째 결정을 남기고 종료합니다. 열려 있는 세션에서 `/codex-memory`의 **Create memories now**를 고른 뒤 설정된 최근 기간을 선택합니다. 그 대화는 1분 대기 없이 기억이 되어야 하고, 다른 세션의 상태 표시줄에 작업이 보여야 합니다.
6. 한 세션에서 세 결정을 묻습니다. 그다음 기억을 끕니다.

macOS, Pi 1.4.0에서 검사 12개가 모두 통과했고 358초 걸렸습니다.

- 작업을 맡은 세션은 하나였고, 강제로 종료한 뒤 90초 만에 다른 세션이 이어받았습니다.
- 대화마다 한 번씩 기억이 되었습니다. 추출 3번과 요약 갱신 3번, 모두 6번 모델을 호출했고 입력 16,552토큰, 출력 6,625토큰을 썼습니다.
- **Create memories now**는 대화를 닫은 뒤 5.1초 만에 끝났고, 다른 세션에는 `Memory: on · creating 1 memory…`가 보였습니다.
- 세션은 `amber`, `blue-7`, `zephyr-ops`를 답했습니다.
- 기억을 끄자 강제로 종료한 프로세스가 남긴 것까지 열림 기록과 작업 임대가 모두 지워졌습니다.

### 회상 시나리오

1. 16턴짜리 합성 대화를 만듭니다. 첫 턴에서 `service`를, 중간 턴에서 `region`과 `verify_command`를 정하고, 마지막 턴에서 `release_gate`를 다른 값으로 정정합니다. "이 프로젝트에만 적용한다"와 "명령은 실행하지 않았다"도 대화에 남깁니다. 값은 실행할 때마다 무작위로 만들어 모델이 미리 알 수 없습니다.
2. 대화를 수동으로 압축하고 한 턴을 더 진행합니다.
3. 이 대화에서 기억을 생성합니다.
4. 새 세션에서 정답이 들어 있지 않은 질문으로 `service`, `region`, `verify_command`, `release_gate`, `decision_scope`, `actions_executed` 여섯 항목을 묻습니다. 답이 기억 도구로 실제로 읽은 줄을 인용하는지도 확인합니다.

| 이름 | 모델 | 추론 강도 |
| --- | --- | --- |
| Haiku | `claude-bridge/claude-haiku-5-5` | 대화·조회 `medium`, 추출 `low`, 통합 `medium` |
| Luna | `openai-codex/gpt-6-luna` | 모두 `high` |

macOS, Pi 1.4.0, Node.js 24.14.0에서 조건마다 한 번씩 실행했습니다.

### 회상

| 모델 | 기억 끔 | 기억 켬 |
| --- | --- | --- |
| Haiku | 0/6. 모두 "모른다"고 답함 | 6/6 |
| Luna | 0/6. 모두 "모른다"고 답함 | 6/6 |

기억을 켠 두 경우 모두 기억 파일을 실제로 읽었고 읽은 줄을 올바르게 인용했습니다. 기억을 끈 경우 "모른다"고 답한 것은 추측하지 말라는 지시를 따른 결과입니다.

압축한 뒤에도 원래 사용자 발언 16개가 모두 추출 입력에 들어갔습니다. 압축 요약 대신 현재 분기의 원래 발언을 추출에 쓰기 때문입니다.

### 토큰과 시간

| 모델 | 생성 토큰 | 생성 시간 | 조회 토큰 | 조회 시간 |
| --- | ---: | ---: | ---: | ---: |
| Haiku | 38,632 | 20.8초 | 14,040 | 10.3초 |
| Luna | 21,822 | 18.9초 | 10,940 | 11.0초 |

- 생성은 추출 1번과 통합 1번, 모델 호출 2번입니다. 조회는 질문 하나에 답하기까지의 모든 모델 호출입니다. Haiku는 2번, Luna는 4번 호출했습니다.
- 토큰은 입력, 출력, 캐시 읽기, 캐시 쓰기를 더한 값이고 Pi가 기록한 `totalTokens`와 같습니다. 요금은 공급자와 요금제에 따라 다릅니다.
- 시간은 모델 호출 시간만 더한 값입니다. 호출 사이 대기와 도구 처리 시간이 빠져 있어 화면에서 느끼는 시간과 다릅니다.

기억 없이 같은 질문을 하면 Haiku는 3,453토큰, Luna는 1,156토큰을 썼지만 답을 얻지 못했습니다.

### 정정과 잊기

- **대화로 정정**: 후속 턴에서 `release_gate`를 다시 바꾸고 기억을 다시 생성했습니다. 두 모델 모두 새 세션에서 바뀐 값을 포함해 여섯 항목을 모두 답했습니다.
- **메뉴로 잊기**: 기억 메뉴에서 기억을 잊고, 대화를 실제로 압축한 뒤 유휴 대화를 수동으로 다시 처리했습니다. 활성 기억, 잊은 사실의 검색 결과, 요약 주입이 모두 0이었고 기억이 다시 생기지 않았습니다. 잊은 뒤 모델에게 다시 묻는 검사는 질문을 잘못 만들어 실패했습니다. 파일이 하나도 없어야 한다고 물었지만 빈 `memory_summary.md` 서식은 남습니다. 고친 질문으로는 다시 실행하지 않았습니다.
- **터미널 검사**: 이보다 앞선 버전으로 실제 터미널에서 새 세션 회상, 메뉴로 정정·잊기, 취소, 재시작과 `/reload`를 확인했습니다. 잊은 값은 90초 동안 자동 재검사를 지켜봐도 다시 나타나지 않았습니다.

### 이 검증의 한계

- 합성 대화 한 종류와 모델 두 개로 조건마다 한 번씩 실행한 결과입니다. 오랜 기간 실제로 사용하며 측정한 결과가 아닙니다. 작업 분담 검사는 모델 하나로 한 번 실행했습니다.
- 원본 요청·응답 기록은 공개하지 않습니다. `verification/live`, `verification/compaction`, `verification/regeneration`의 회상 검증 스크립트는 이 기록을 입력으로 쓰므로 저장소만으로는 다시 실행할 수 없습니다. `verification/live/coordinator.py`는 이런 기록이 필요 없습니다.

## 기본값을 정한 방법

기본값은 소유자가 정했습니다. 닫은 대화는 마지막 메시지 뒤 2시간이 지나면 기억이 되고, 요약은 최대 2시간에 한 번 갱신하며, 최근 7일 안의 대화를 씁니다. Codex는 6시간, 6시간, 10일을 씁니다. Codex는 작업을 시작한 세션만 빼고, 나머지 대화는 열려 있는지와 상관없이 멈춘 시간만으로 판단합니다.

모델 호출은 10분 뒤에 멈춥니다. `claude-sonnet-5-5`를 `xhigh` 추론으로 쓰면 약 256 KiB의 기억을 합치는 요약이 이전 기본값인 2분 안에 끝나지 않았습니다.

닫은 대화만 기억이 되므로, 대기 시간은 더 이상 진행 중인 작업에서 추출을 막는 역할을 하지 않습니다. 방금 닫은 대화를 다시 열 수 있는 시간을 두는 역할을 합니다. 다시 열어 이어 간 대화는 다시 추출합니다.

### 언제 바꾸면 좋은가

`/codex-memory-settings`에서 바꿉니다.

- 다음 작업에 기억이 너무 늦게 생기면 **Create memories after**를 30분이나 60분으로 줄입니다. 그 시간 안에 다시 열어 이어 간 대화는 다시 추출하므로 호출이 늘어납니다.
- 호출을 줄이려면 **Update the summary every**를 3시간이나 6시간으로 늘립니다.
- 더 오래된 작업까지 넣으려면 **Use conversations from the last**를 늘립니다. 다음 확인 때 지난 대화를 더 많이 처리합니다.
- **Show what failed**에 `timeout`이 보이면 **Stop a model call after**를 늘리거나 그 모델의 추론 강도를 낮춥니다.
- 기억이 바로 필요하면 닫은 대화는 `/codex-memory`의 **Create memories now**를, 지금 대화는 `/codex-memory-settings`의 **Remember this conversation now**를 씁니다.
