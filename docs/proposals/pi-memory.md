# Pi 메모리 도입 제안과 `/memory` 관리 화면

- 상태: 도입 제안. 확장·명령·설정은 아직 구현하지 않았다.
- 작성일: 2026-10-23
- 대상: Pi 패키지 유지보수자와 향후 메모리 확장 구현자
- 검토 기준: Codex 커밋 `4610b573e59b211bf9430cf6ffb97cfb84623090`, 설치 Pi `1.4.0`
- 자문: `openai-codex/gpt-6-astra:max` 하위 에이전트 2개의 독립 의견과 메인 소스 대조

## 1. 권장 방향과 확정된 문서 요구

**Codex v2의 출처 보존·작은 문맥 주입·선택 조회를 Pi 독립 확장으로 도입하는 것을 권한다.** Codex의 전역 자동 수집·모델 통합을 그대로 복제하지 않고, 사용자가 기억의 내용과 적용 범위를 관리할 수 있는 기능부터 시작한다.

사용자가 지정한 요구는 **`/memory` 명령 하나를 메모리 관리의 진입점으로 제공하고, 그 내부에서 메모리 관련 설정을 바꿀 수 있게 하는 것**이다. 설정 파일 수동 편집이나 여러 개의 별도 슬래시 명령을 기본 사용 경로로 삼지 않는다.

이 문서에서 그 외의 저장 방식, 기본값, 단계별 기능은 권장안이다. 문서 저장·커밋·푸시는 기능 구현이나 자동 모델 호출의 승인을 뜻하지 않는다. 구현 범위를 선택할 때는 다음 순서를 권한다.

1. `/memory` 관리 화면과 명시적 기억·조회·정정·잊기
2. 사용자가 선택한 현재 분기의 요청형 요약 추출
3. 효과와 비용을 확인한 뒤 선택적으로 켜는 자동 후보 수집

첫 단계에는 추가 추출 모델 호출을 넣지 않는다. 이후 단계도 같은 `/memory` 화면 안에서 설정하고 관리한다.

## 2. 왜 메모리가 필요한가

메모리는 과거 결정의 이유, 사용자 정정, 작업의 완료·미완료 상태를 다음 세션으로 연결한다. 이미 다른 곳에서 관리하는 규칙을 중복 저장하는 기능이 되어서는 안 된다.

| 정보 | 우선하는 위치 | 메모리의 역할 |
|---|---|---|
| 지속적으로 지켜야 하는 작업 규칙 | 사용자가 채택한 `AGENTS.md` 등 프로젝트 지침 | 지침을 복제하거나 덮어쓰지 않음 |
| 반복 수행 절차 | 스킬 | 적용했던 상황과 결과의 출처를 보충 |
| 현재 구현의 사실 | 소스 코드·현재 검증 결과 | 과거 결과를 찾는 경로 제공. 현재 사실을 대신하지 않음 |
| 과거 결정·정정·미완료 작업 | 출처가 있는 장기 메모리 | 범위·시점·확인 상태를 유지하며 재사용 |

예를 들어 이번 분석에서 보존할 만한 것은 보고서 위치, 검토한 설계 대안, 아직 구현하지 않았다는 상태다. “이번 요청에서 Astra 두 개의 의견을 받았다”를 “사용자는 항상 두 에이전트의 검토를 원한다”로 일반화해서는 안 된다.

도입하지 않으면 추가 저장·운영 비용은 없지만, 세션을 넘을 때 이전 결정을 다시 설명하거나 원문을 찾아야 한다. 도입 가치는 그 반복 비용이 기억을 검토·정정하는 부담보다 큰지에 달려 있다. 실제 생산성 향상이나 비용 절감은 아직 측정하지 않았다.

## 3. 두 자문 의견과 대안 비교

### 3.1 공통점과 이견

| 항목 | 구현 관점 | 안전성·운영 관점 | 종합 판단 |
|---|---|---|---|
| 도입 여부 | 제한적 도입 권장 | 제한적 도입 권장 | 출처·범위가 있는 기억부터 도입 |
| 소유권 | `apps/pi-memory` 독립 확장 | 지침·스킬과 분리된 저장소 | 공급자 중립 패키지로 분리 |
| 첫 버전 | 명시적 저장과 요청형 현재 분기 추출 | 모델 호출 없는 저장·조회부터 | 저장·조회·정정의 효용을 먼저 확인 |
| 자동 수집 | 나중에 추가 | 삭제·오염·비용 통제 이후 추가 | 기본 꺼짐, 후속 단계로 분리 |
| 제외할 기능 | 전역 통합, 이중 쓰기, 자동 스킬 생성 | 전역 선호 추론, 인용 횟수 기반 보존 | 초기 범위에서 모두 제외 |

이견은 추출 모델을 첫 버전부터 포함할지다. 먼저 기억의 관리와 조회가 유용한지 확인하면, 추출 실패와 모델 비용을 저장소 결함과 분리해 판단할 수 있다. 다만 사용자가 기록을 직접 만드는 부담이 크면 요청형 추출 단계의 우선순위를 높일 수 있다.

### 3.2 선택 가능한 도입 범위

| 대안 | 장점 | 비용·위험 | 판단 |
|---|---|---|---|
| 현 상태 유지 | 새 저장소·자동 호출·설정 없음 | 반복 설명과 과거 기록 탐색을 계속 수행 | 반복 비용이 낮다면 합리적 |
| 관리형 기억 확장 | 출처·범위·정정·삭제를 명시적으로 제어 | 저장소와 관리 화면 유지 필요 | 권장 시작점 |
| 전역 자동 기억 | 기록 작성 부담을 줄일 가능성 | 추가 모델 비용, 오염·과잉 일반화·재생성·동시성 문제 | 초기 도입으로는 보류 |

## 4. `/memory`를 단일 관리 진입점으로 제공한다

### 4.1 첫 화면

사용자가 `/memory`를 입력하면 현재 작업 공간의 메모리 상태와 관리 메뉴를 연다. 화면을 여는 것만으로 추출 모델을 호출하거나 저장 자료를 변경하지 않는다.

상단에는 다음을 표시하는 구성을 권한다.

- 현재 기억 범위와 연결된 작업 공간
- 에이전트의 기억 사용 여부와 자동 주입 여부
- 수집 모드: 꺼짐·요청형·자동 후보 수집
- 활성 기록·삭제 제외 기록 수
- 추출 기능이 도입된 경우 대기·실행·실패 작업과 사용량
- 유효 설정의 출처: 개인 기본값·작업 공간·현재 세션

메뉴는 다음처럼 구성한다.

| 메뉴 | 내부 동작 | 도입 단계 |
|---|---|---|
| 기억 조회 | 범위 내 검색, 본문·출처·수정 이력·확인 상태 열람 | 1 |
| 기억 추가·정정 | 승인된 문구와 적용 범위를 확인해 저장 | 1 |
| 기억 잊기 | 선택 기록과 파생 캐시 제외, 재등장 방지 상태 반영 | 1 |
| 설정 | 사용·범위·주입·수집·모델·예산·보존 항목 편집 | 단계별 확장 |
| 상태·사용량 | 현재 적용값, 작업 상태, 저장 위치, 실패 이유 표시 | 1, 모델 작업 정보는 2 이후 |
| 현재 분기에서 추출 | 사용자가 지정한 대화 범위의 요약 후보 생성 | 2 |
| 작업 관리 | 대기 작업 취소, 실패 확인, 허용 범위 내 재시도 | 2 |
| 초기화 | 대상과 영향을 확인한 뒤 기억·색인 초기화 | 1 |

아직 구현하지 않은 항목은 숨기거나 “추후 지원”으로 표시하고, 설정값만 저장해 동작하는 것처럼 보이게 하지 않는다. `/memory-settings`, `/memory-model`, `/memory-reset` 같은 별도 최상위 명령으로 기능을 분산하지 않는다.

### 4.2 설정은 화면 안에서 편집·검토·저장한다

권장 조작 흐름은 다음과 같다.

1. `/memory`에서 **설정**을 선택한다.
2. 수정할 적용 범위와 항목을 고른다.
3. 현재 유효값, 상속한 값, 변경 후 영향을 함께 보여준다.
4. **저장**을 누르면 검증한 값을 영속화하고 적용한다. **취소**하면 기존 값을 유지한다.
5. 저장 결과와 적용 시점을 표시하고 관리 화면으로 돌아간다.

변경 내용을 저장하기 전에는 실제 동작을 바꾸지 않는다. 자동 수집이나 모델 전송을 켜는 변경은 전송 대상·공급자·비용 조건을 보여준 뒤 확정한다. 읽기 중지, 정정, 잊기는 새 모델 호출 없이 처리한다.

설정 저장에 실패하면 성공으로 표시하지 않는다. 저장과 런타임 적용이 분리되는 경우에는 이전 유효값을 유지하거나 적용 대기 상태를 명확히 표시해, 디스크 값과 실제 동작이 조용히 달라지지 않게 한다.

### 4.3 내부 설정 항목

다음 기본 동작은 제품 설계 제안이며, 현재 구현된 Pi 메모리 설정이 아니다.

| 분류 | 사용자가 바꾸는 항목 | 권장 초기 동작·경계 | 단계 |
|---|---|---|---|
| 기억 사용 | 에이전트 조회·주입 활성화 | 기본 꺼짐. 관리 화면은 계속 접근 가능 | 1 |
| 적용 범위 | 현재 작업 공간, 명시적으로 연결한 프로젝트·작업 트리, 개인 전역 | 현재 작업 공간만 사용. 공유 확대는 별도 확인 | 1 |
| 문맥 주입 | 자동 주입 여부, 최대 크기, 조회 결과 수 | 주입은 별도 선택. 표식·출처를 포함한 바이트 예산 관리 | 1 |
| 수집 | 꺼짐, 요청형 추출, 자동 후보 수집 | 기본 꺼짐. 자동 수집을 주입 활성화와 묶지 않음 | 2~3 |
| 추출 모델 | 공급자, 모델, 추론 강도 | 명시적으로 선택. 현재 대화 모델 변경에 따라 몰래 바뀌지 않음 | 2 |
| 전송·처리 예산 | 입력·출력 한도, 작업 시간, 재시도, 호출 횟수·비용 제한 | 유효한 제한을 정하기 전에는 추출 시작 안 함 | 2 |
| 보존 | 명시적 만료, 고정 기억, 정정·삭제 정책 | 자동 내용 삭제는 기본 꺼짐. 정정·삭제 제외 상태를 일반 보존 기간으로 만료시키지 않음 | 1 |
| 자동화 | 유휴 조건, 회당 처리량, 동시 실행 수 | 전경 작업 우선. 정해진 한도 안에서만 처리 | 3 |
| 개인정보 | 추출에 포함할 정보 종류, 외부 자료 포함 여부 | 외부 자료 자동 수집 제외. 전송·저장 마스킹을 사용자가 우회하는 옵션은 두지 않음 | 2~3 |

주입 예산은 초기 실험값으로 약 4 KiB처럼 작게 시작할 수 있다. 이는 검증된 최적값이 아니며, 한국어 문맥과 모델별 여유를 관찰해 조정한다. 토큰당 4바이트 같은 근사치를 실제 모델 토큰 상한으로 표현하지 않는다.

모델이 가격 정보를 제공하지 않으면 금액 한도를 보장할 수 없다. 이 경우 추정치와 미확인 상태를 구별하고, 호출 횟수·입출력·시간 제한처럼 직접 적용 가능한 한도를 사용한다. Codex의 6시간·30일·256개를 근거 없이 기본값으로 복사하지 않는다.

### 4.4 설정 범위와 적용 시점

일반 설정은 **현재 세션 덮어쓰기 → 작업 공간 설정 → 개인 기본값 → 확장 기본값** 순서로 해석하는 안을 권한다. 현재 세션 덮어쓰기는 범위가 드러나야 하며 세션 재개와 분기 이동 때 복원 계약을 유지해야 한다.

다만 외부 모델 전송 허용, 개인 전역 공유처럼 권한을 넓히는 선택은 일반 상속 규칙으로 자동 활성화하지 않는다. 개인 정책이 금지한 동작을 작업 공간 설정으로 허용해서는 안 된다.

| 변경 | 권장 적용 방식 |
|---|---|
| 기억 사용 끄기 | 다음 요청부터 주입·에이전트 조회를 중단. 관리 화면과 저장 자료는 유지 |
| 자동 주입만 끄기 | 다음 요청부터 자동 추가만 중단. 에이전트 조회 허용 여부는 기억 사용 설정을 따름 |
| 수집·추출 끄기 | 새 예약을 막고 실행 중 작업을 취소. 완료 직전 결과도 저장 허용 상태를 재확인 |
| 조회 범위 변경 | 범위별 캐시를 무효화하고 다음 조회부터 새 범위 적용 |
| 모델·한도 변경 | 새 작업에 적용. 진행 중 작업은 시작 시 설정을 표시하고 취소·재예약 선택 제공 |
| 정정·잊기 | 새 조회와 주입에서 이전 내용을 즉시 제외하고 오래된 작업의 재등록 차단 |
| 보존 기간 축소 | 삭제 대상 수와 범위를 미리 보여준 뒤 적용. 삭제 표식과 재수집 방지 상태는 별도 관리 |

개인·작업 공간 설정은 `getAgentDir()` 아래 확장 전용 저장 영역에 두는 안을 권한다. 저장소나 설치 패키지에 비공개 기억과 설정을 자동으로 작성하지 않고, 호스트가 알지 못하는 키를 Pi 공용 설정에 임의로 추가하지 않는다.

### 4.5 터미널 외 모드

`/memory`의 전체 관리 화면은 TUI를 기본으로 한다. RPC에서는 지원하는 대화상자나 텍스트 메뉴로 같은 기능에 접근하도록 하고, `ctx.hasUI`와 `ctx.mode`를 구별한다.

텍스트 진입이 필요하면 `/memory status`, `/memory settings`처럼 **같은 명령 아래의 하위 동작**을 제공하는 안을 검토한다. 별도 최상위 명령을 늘리지 않는다. 이 문법은 아직 구현되지 않았다.

대화상자가 없는 실행에서는 상태를 읽기 전용으로 보여주고, 필요한 확인을 받을 수 없는 설정 변경·삭제·외부 전송은 취소한다. 지원하지 않는 사용자 인터페이스를 호출해 멈추거나, 확인 부재를 승인으로 처리하지 않는다.

## 5. 기억 저장과 조회 구조

### 5.1 하나의 권위 저장소

실제 패키지에는 **SQLite를 권위 저장소로, 마크다운을 검토·내보내기용 파생물로 사용하는 방식**을 권한다. 수동 노트만 다루는 단일 프로세스 시제품은 파일만으로도 가능하지만, 여러 Pi 프로세스와 추출 작업을 다루려면 결국 잠금·중복 처리·삭제 상태 장부가 필요하다.

DB와 마크다운을 각각 편집 가능한 원본으로 운영하지 않는다. 기록에는 다음 정보를 보존한다.

- 기억 식별자와 수정 버전
- 승인된 내용과 적용 범위
- 출처 세션·항목 식별자와 확인 시각
- 사용자 직접 발언, 에이전트 제안, 압축·분기 요약 등 증거 종류
- 완료·실패·미검증·대체됨 등 작업 상태
- 고정·만료·정정·삭제 제외 상태

원문 전체를 불필요하게 복사하지 않는다. 사용자 전역 선호로의 승격은 명시적으로 선택한 경우만 허용한다. 작업 디렉터리 변경이나 작업 트리 공유도 자동 병합하지 않는다.

### 5.2 작은 문맥과 선택 조회

문자열 검색과 기록 식별자 기반 상세 조회부터 시작한다. 에이전트용 도구가 필요하면 `pi_memory_search`, `pi_memory_read`처럼 패키지 식별자가 있는 이름을 사용한다. 이는 사용자용 `/memory` 관리 명령과 별개의 도구 표면이다.

기억은 관련 기록의 짧은 내용과 출처만 요청 문맥에 제공한다. 과거 자료임을 표시하고 현재 지침·현재 소스·실행 승인으로 취급하지 않는다. 매번 세션 기록에 같은 기억을 추가하면 재추출 순환이 생기므로 요청 단위 주입을 우선한다.

`before_agent_start`에서 사용할 범위를 준비하고 `context`에서 요청용 사본을 추가하는 방식은 가능한 선택지다. 반면 `before_agent_start`가 반환하는 사용자 정의 메시지는 세션에 저장될 수 있으므로 두 경로를 혼동하지 않는다. 실제 프롬프트 캐시 영향은 구현 후 측정해야 한다.

## 6. 요청형 추출과 향후 자동 수집

### 6.1 요청형 추출

2단계에서 `/memory` 내부의 **현재 분기에서 추출**을 제공한다.

1. 사용자가 현재 분기의 대상 범위를 선택한다.
2. 전송 대상·모델·한도를 표시하고 입력 사본을 고정한다.
3. 마스킹한 자료를 모델에 전달해 기억 후보를 만든다.
4. 후보별 내용·적용 범위·출처·불확실성을 보여준다.
5. 사용자가 선택한 후보를 저장한다. 선택하지 않은 후보는 활성 기억으로 사용하지 않는다.

빈 결과는 정상 결과다. 실패한 작업의 교훈도 저장할 수 있지만 “실패·미검증” 상태를 보존하며, 실패 응답을 완료된 사실로 바꾸지 않는다.

### 6.2 Pi의 분기와 문맥 편집

`getEntries()`는 버린 분기를 포함할 수 있고, `getBranch()`도 현재 경로의 원시 항목을 반환한다. 자동 추출에서는 문맥 편집·압축을 반영한 `buildSessionProjection()` 등과 출처 정보를 함께 고려해야 한다.

현재 분기에 포함된 분기 요약도 사용자의 직접 발언은 아니다. 이전에 주입한 기억, 추출 결과, 하위 에이전트 답변을 새로운 사용자 증거로 다시 수집하지 않는다. `parentSession`은 일반 분기·복제에도 사용되므로 하위 에이전트 판별 근거 하나로 삼지 않는다.

### 6.3 자동 수집의 실행 경계

Pi의 `agent_end` 뒤에는 후속 실행이 남을 수 있다. `agent_settled`는 자동 후속 처리가 끝난 알림이지만 처리기를 기다리므로, 그 안에서 긴 추출 모델 호출을 기다리면 완료가 지연된다.

자동 수집을 도입할 때는 다음 구조가 필요하다.

- 완료 상태와 출처를 확인한 뒤 짧게 작업만 예약한다.
- 별도 실행기가 유휴 상태에서 정해진 한도 안에서 처리한다.
- 새 사용자 작업, 분기 이동, 재로딩, 세션 교체·종료 때 취소한다.
- 입력 지문·추출기 버전·작업 소유권으로 중복을 막는다.
- 모델 호출 중 DB 트랜잭션을 열어두지 않는다.
- 완료 시 현재 설정, 소유권, 삭제 상태, 작업 세대를 다시 확인한다.
- 공급자 재시도와 작업 재시도가 중첩되지 않도록 전체 예산을 관리한다.

유휴 이벤트에는 `ctx.signal`이 없을 수 있으므로 실행기 자체의 취소 수단이 필요하다. 프로세스 내부 큐만으로 다른 Pi 프로세스까지 잠글 수 없으며, 종료 훅에서 새 추출을 시작해서도 안 된다. 이 구조는 Pi 종료 뒤에도 계속 실행되는 상주 서비스가 아니다.

## 7. 안전성과 삭제 계약

### 7.1 마스킹을 별도 모델 호출까지 연결한다

`ctx.modelRegistry.streamSimple()` 같은 직접 모델 호출은 메인 세션의 문맥 처리기를 자동으로 모두 거치지 않는다. 따라서 `pi-redact` 설치만으로 추출 요청이 보호된다고 가정해서는 안 된다.

메모리 확장은 [공유 마스킹 라이브러리](../../packages/redact/src/index.ts)를 사용해 **전송 직전과 저장 직전에 자체 마스킹**하는 구조를 가져야 한다. 실패하면 원문 전송·저장을 중단한다. 기존 확장의 연결 위치는 [`pi-redact` 처리기](../../apps/pi-redact/src/index.ts)에서 확인할 수 있다.

마스킹이 모든 개인정보를 탐지한다는 보장은 없다. 원문을 포함하는 진단 로그를 새로 만들지 않고, 기억 내용을 시스템 지침에 합쳐 기존 마스킹 경계를 우회하지 않는다. 메모리는 로컬에 저장되어도 추출 입력은 선택한 공급자로 전송될 수 있다.

### 7.2 정정·잊기·초기화를 구별한다

| 동작 | 권장 계약 |
|---|---|
| 정정 | 새 버전을 활성화하고 이전 내용·파생 캐시를 조회에서 제외 |
| 잊기 | 내용 삭제와 재등장 방지 표식을 함께 반영 |
| 기억 사용 중지 | 에이전트 조회·주입을 멈추되 관리 화면과 저장 자료는 유지 |
| 수집 중지 | 새 작업을 막고 실행 중 추출을 취소 |
| 초기화 | 선택 범위의 기억·색인을 비우고 작업 세대 변경. 과거 재수집 방지 상태는 기본 유지 |
| 원본 삭제 | Pi 세션·내보내기·별도 분석 기록 등 원본과 사본을 별도로 처리 |

삭제 표식에는 잊은 원문을 복사하지 않는다. 수집을 도입하면 출처·분기·입력 버전별 처리 워터마크도 필요하다. 초기화 뒤 과거 자료를 다시 수집하려면 사용자가 그 영향을 확인하고 명시적으로 선택해야 한다.

기존 대화가 기억을 바탕으로 이미 생성한 문장, 다른 확장의 분석 저장소, 공급자로 전송한 요청까지 모두 삭제했다고 표시해서는 안 된다. `/memory`의 삭제 확인 화면에는 대상 범위와 남는 사본을 구별해 안내한다.

### 7.3 기억은 실행 권한이 아니다

이전 작업의 승인, 프로젝트 신뢰, 기억 저장 승인을 새로운 파일 변경·배포·외부 게시의 승인으로 승격하지 않는다. Pi 확장은 호스트 프로세스 권한으로 실행되므로 프로젝트 신뢰나 프롬프트만으로 샌드박스가 생기지 않는다.

`AGENTS.md`·스킬을 메모리에서 자동 수정하거나 생성하는 기능은 초기 범위에 넣지 않는다. 외부 파일이나 웹 문서의 문장을 사용자의 선호로 저장하지 않는다.

## 8. 패키지와 호환성 경계

기능 소유자는 제안 경로 `apps/pi-memory`다. 모델 공급자 중립 기능이므로 초기에는 `pi-codex` 묶음과 분리한다. 최소 범위에 필요한 명령·문맥 변환·분기 조회·별도 모델 호출 API는 설치 Pi `1.4.0`에서 확인했으며, 이 범위는 코어 수정 없이 구현할 수 있는 것으로 판단한다.

패키지 구성은 기존 컴파일형 확장과 맞추는 안을 권한다.

- `src/`에서 구현하고 `pi.extensions`에 실제 `dist/` 진입점을 선언한다.
- 가져오는 호스트 패키지만 `peerDependencies`의 `"*"`로 선언한다.
- 호스트 런타임 사본을 묶거나 내부 `dist/` 경로를 직접 가져오지 않는다.
- 프롬프트 등 필요한 자산은 실제 배포 파일에 포함한다.
- 기억·설정·작업 장부는 설치 디렉터리 밖에 둔다.
- `/memory` 이름 충돌을 로딩 검증에서 확인하고 기존 명령을 조용히 덮어쓰지 않는다.

[공통 개발 카탈로그](../../pnpm-workspace.yaml)는 조사 당시 Pi `1.3.0`을 사용했다. 설치 `1.4.0`에서 확인한 API를 채택한다면 새 패키지의 개발·검증 기준을 맞춰야 한다. 이를 이유로 다른 앱까지 일괄 업그레이드하지 않는다. 버전 문자열만으로 설치본의 정확한 빌드 커밋이나 공급자별 동작이 같다고 단정하지 않는다.

참고한 `pi-package-creator` 스킬은 Pi `v1.4.0` 태그 커밋 `4a080252f06caf63a525d7873c5d94d3c23887e0`을 대상으로 한다. 문서와 실제 설치 구현이 다르면 구현을 확인하고 차이를 기록해야 한다.

## 9. 도입 단계와 판단 기준

| 단계 | 포함 | 제외 | 다음 단계 판단 기준 |
|---|---|---|---|
| 1. 관리형 기억 | `/memory` 화면·설정, 명시적 저장·조회·정정·잊기, 범위 제어, 선택적 주입 | 추출 모델 호출, 세션 전수 수집 | 반복 설명이 줄고 정정·삭제가 예측 가능함 |
| 2. 요청형 추출 | 현재 분기 범위 선택, 후보 생성·선택, 모델·예산 설정, 작업 상태 | 자동 수집, 전역 선호 추론 | 수동 작성 부담 감소가 검토·비용 부담보다 큼 |
| 3. 선택적 자동화 | 제한된 자동 후보 수집, 중복 방지, 전경 우선·취소, 사용량 관리 | 무제한 수집, 자동 스킬 생성 | 오기억·재등장·지연·비용이 허용 범위 안에 있음 |

인용은 출처 표시로 사용하고 초기 보존 순위 점수로 쓰지 않는다. 자주 인용된 오류가 오래 남는 순환을 피하기 위해 사용자 고정·정정·명시적 만료를 우선한다. 벡터 검색, Git 차이 기반 전역 통합, 이중 쓰기는 실제 조회 문제와 규모가 확인되기 전까지 보류한다.

기억 개수보다 다음 결과가 중요하다.

- 이전 결정을 다시 설명하는 횟수의 변화
- 잘못되거나 오래된 기억을 사용한 빈도
- 사용자의 정정 부담과 삭제 내용의 재등장 여부
- 전경 작업 지연과 별도 모델 호출 사용량
- 다른 프로젝트·분기·하위 에이전트 자료가 섞였는지

비용·기간·적정 예산의 수치는 아직 산정하지 않았다. 1단계는 추가 모델 추출 비용이 없지만 저장소·관리 화면·조회 정확성을 유지하는 비용은 있다. 자동 수집이 꺼져 있어도 명시적으로 저장한 자료를 계속 관리할 수 있어야 한다.
